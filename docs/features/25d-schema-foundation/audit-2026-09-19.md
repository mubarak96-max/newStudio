## Findings

### CRITICAL — the runtime is still a prototype renderer, not the canonical visual contract

- `src/features/book-experience/preview/DepthScene.tsx:11-15` maps roles to colors; `:28-35` synthesizes a sine-wave depth surface; `:42-44` creates a colored material. The plane/depth-mesh branches at `:89-100` never load `layer.image` or `layer.depth`.
- `src/features/book-experience/preview/CssFallback.tsx:6-10` defines role colors and `:47-60` renders colored blocks with layer-id text instead of image assets.
- `src/features/book-experience/preview/EpisodePreview.tsx:291-304` selects those implementations. Both the WebGL stage (`:299`) and CSS fallback (`CssFallback.tsx:32`) hard-code `16 / 9`, while the supplied composed fixture is portrait-oriented.
- Responsive-crop logic is unit-tested separately but is not consumed by either renderer. The browser check at `tests/book-experience/preview.spec.ts:63-70` checks a subtitle bounding box, not crop correctness or image coverage.

Result: P2's “done” claim and P9's qa-pending demo outcome are not met. The required canonical image/depth layers, plane/depthMesh behavior, responsive crops, and equivalent CSS fallback are not implemented end to end. A prototype color/geometry shape has silently replaced the canonical rendering contract.

Positive evidence: DOM subtitles, reduced-motion branching, and subtitle escaping exist at `EpisodePreview.tsx:51-69,100-107,270-276,307-322` and `src/features/book-experience/functions/subtitles.ts:7-13,28-42`. This does not offset the missing asset renderer.

### CRITICAL — visual “validation” trusts fabricated metadata rather than output bytes

- `worker/visuals/generate.mts:107-122` assigns requested width/height, creates a `fake-...` checksum, infers alpha only from target kind, hard-codes depth bit depth to 8, copies requested overscan, and sets text detection false.
- The provider result at `worker/providers/images.mts:18-23,38-51` contains bytes/content type/model/cost, but generation never decodes those bytes to prove transparency, dimensions, depth precision, alignment, overscan, or text absence.
- `src/features/book-experience/visuals/assets.ts:32-76` validates the resulting descriptor claims, not the asset.
- `worker/visuals/generate.mts:148` starts continuity as pending. `approveVisualGeneration` at `:155-167` checks descriptors only, then `src/features/book-experience/visuals/repository.ts:97-101` promotes continuity to approved without an artistic or geometric comparison.
- `src/app/api/books/[bookId]/visuals/route.ts:60-77` accepts a client target/kind. When no existing visual request is present, reference pins are empty and `:121-129` has nothing meaningful to enforce.

Result: P8's “done” claim is false. Transparent-output validation, truthful depth metadata, reference pins, and continuity gates are incomplete code, not merely owner-quality checks. Real provider quality, artistic continuity, and device quality remain unverified and owner-only.

### CRITICAL — source approval points at canonical storage that production code never writes

- `src/app/api/books/[bookId]/sources/[sourceId]/approve/route.ts:79-145` computes a canonical hash and updates source/book metadata, but does not upload `canonical.json` or write the required paragraph chunks.
- `worker/ingest.mts:43-48` describes materialization in a comment, while `previewCanonical` at `:50-67` only validates input and returns counts.
- Actual materialization exists only in the fake repository at `src/features/book-experience/storage/repository.ts:130-163`.

Result: P3's “done” claim is false for the production path. The fixture proves an in-memory round trip, not immutable storage materialization or correction invalidation in the active system.

### CRITICAL — the canonical P4–P9 pipeline is not wired into the active worker or owner UI

- `worker/index.mts:24-28,58-65` still claims work from the legacy `allJobs` document. It does not import or dispatch the canonical job engine, book-model planner, story planner, Beat planner, visual generator, or composition assembler.
- `src/features/library/components/book-detail.tsx:10-20,67-70` still reads the legacy `ALL_JOBS_DOC` flow.
- `src/features/sources/components/extraction-editor.tsx:8-11,320-360` still renders the legacy Book Bible, Episode Map, and Image Studio surfaces.
- The new BookModelReview, StoryMapReview, EpisodeBoard, BeatReview, and VisualReview components have declarations/tests but no active app imports. Only the compose preview has an app route.
- The active UI still asks for manual data: chapter title (`extraction-editor.tsx:246-258`), Bible text/evidence/reveal (`book-bible.tsx:396-415`), episode title/purpose/boundary/reason (`episode-map.tsx:298,340,392-409,512`), story moment scene/data fields (`story-moments.tsx:334,399,437,484-499`), prompt additions (`studio-reference.tsx:191-204`, `moment-images.tsx:68-78`), and focal/safe numeric inputs (`moment-images.tsx:141-161`).

Result: the approval → visual selection/generation → preview owner journey cannot be completed without legacy manual prompt/camera/layer/text/data entry. P4 and P5 are incomplete rather than qa-pending; P6 and P7 “done” claims are not demoable through the product; P8 and P9 are likewise incomplete. `status.md` itself acknowledges the legacy active path.

### CRITICAL — compose is fixture-bound and its approval action is a no-op

- `src/app/studio/books/[bookId]/compose/ComposeWorkspace.tsx:17` hard-codes `harbor-composed` for every book and `:27` loads its fixture endpoint.
- `:48-65` constructs no actionable blockers, and `:68-72` only displays that server approval runs in P10.
- `:94-100` passes an empty blocker list.

Result: P9's real next-action blockers, links/actions, draft handling, and approve-and-continue outcome are not implemented. Source-string tests for labels do not prove the workflow.

### HIGH — approval routes can bypass canonical validation and fingerprint checks

- `src/app/api/books/[bookId]/model/route.ts:44-60` casts request JSON and approves an existing document without parsing the canonical Entity/Event schemas or validating evidence, source/hash pins, or a recomputed fingerprint.
- `src/app/api/books/[bookId]/episodes/route.ts:43-56,76-99` similarly approves story-map/moments state without schema/coverage/fingerprint validation.
- `src/app/api/books/[bookId]/compositions/route.ts:45-75` trusts the client fingerprint and checks only supplied QA issues; it does not parse/recompute the Composition or revalidate continuity, pins, visual metadata, or text detection.
- `src/app/api/books/[bookId]/jobs/approve/route.ts:30-39,69,84-99,118-145` receives a content fingerprint and revision pins but compares only the cursor revision and checkpoint source/hash. A changed client fingerprint can be attached to the same checkpoint and enqueue another successor.
- `src/features/book-experience/jobs/pipeline.ts:65-67` likewise limits its pin comparison to source/hash.

Result: approval can bypass validation, and duplicate-click safety is not proven. Draft placeholders may be explicit in some UI surfaces, but the server boundary does not enforce the complete contract.

### HIGH — schemas are not strict and omit required universal invariants

- Core schemas use `z.object`/`extend` without `.strict()`. A probe showed an unexpected Paragraph field is silently stripped rather than rejected.
- `src/features/book-experience/contracts/planning.ts:88-105,129` models `Episode.stageStatus` as a partial record, so an empty stage map parses even though the contract requires all seven stages.
- `src/features/book-experience/contracts/primitives.ts:7` defines an ISO date as any non-empty string. A probe accepted an invalid date.
- Crop and hotspot fields at `primitives.ts:68-86` constrain individual values to 0..1 but do not require `x + width <= 1` or `y + height <= 1`. A probe accepted an overflowing crop.
- `src/features/book-experience/contracts/composition.ts:25-28` does not require ordered depth ranges.

Probe output:

```text
paragraph-unexpected-preserved false
empty-stageStatus-accepted true
invalid-iso-accepted true
overflow-crop-accepted true
```

Result: the plan's strict-Zod and complete-stage contract is not satisfied.

### HIGH — the bundle compiler does not enforce lineage, semantic Representation coverage, or spoiler views

- `src/features/book-experience/fixtures/compileFixtureBundle.ts:7-22` defines a non-strict fixture shape.
- `:28-51` compares ID collections but does not validate representation source/hash lineage, known paragraph IDs, or semantic meaning.
- `:81-97` always emits empty `entities` and `entityViews`.
- A mutation probe compiled a Moment with a wrong source/hash, meaningless description text, and an unknown `p999999` Representation:

```text
compiled src_room_entry fixture-hash-room-entry-v1 entityViews 0 unknownRepresentationAccepted true
```

- A stronger semantic validator exists at `src/features/book-experience/beats/representations.ts:27-31,58-105`, and UTF-16 quote validation correctly uses JavaScript string slicing at `src/features/book-experience/functions/verbatim.ts:17-53`, but the compiler does not invoke the semantic validator.

Result: UTF-16 exact-quote behavior has machine evidence, but actual cross-boundary round trips, strict coverage, semantic Representation review, and per-Beat spoiler views are not enforced by the bundle compiler. P7 is not complete.

### HIGH — safe-camera proof ignores the inputs required to guarantee a hole-free frame

- `src/features/book-experience/composition/safeCamera.ts:41-60` uses minimum declared background overscan and maximum displacement scale.
- `src/features/book-experience/composition/assemble.ts:190-198` supplies only role, overscan, and displacement scale.
- The calculation ignores actual opaque bounds, alpha, asset dimensions, responsive crop/aspect, transforms, motion, rotation, and depth coverage.

Result: the helper can produce deterministic metadata, but it cannot prove no holes or clipping across ratios and motion. That is incomplete code plus unverified artistic/device quality.

### HIGH — P10 publication is absent; the legacy replacement behavior is historically destructive

- There is no P10 publication module/worker/API/rules implementation and no `smoke:bundles` or `smoke:publishing` package script.
- `src/features/completion/store.ts:199-201` deletes a previous prepared replacement, and `:279-286` deletes the old active version after promotion. `tests/smoke/smoke-completion.mts:17-19` currently expects that deletion.
- The P12 workflow test explicitly states that publication/replacement is not simulated.

Result: independent Episode publication, immutable bundles/assets, atomic race-safe catalog promotion, draft-only regeneration, retained shared assets, old-session validity, progress anchors, and non-destructive rollback/withdrawal have no implementation evidence. The destructive code is a stale legacy adapter, not a completed P10 implementation; it must not become the P10 design.

### HIGH — P11 security/rules and emulator evidence are absent

- Production bypass prevention has good static evidence: `src/features/auth/mode.ts:27-35`, `src/features/auth/session.ts:42-59`, `src/proxy.ts:14-23`, and `src/app/api/dev-token/route.ts:21-24` reject development bypass behavior outside its allowed mode.
- `firestore.rules:15-21` is still the legacy public-read rule for live episodes/story moments; `:30-33` keeps other descendants editor-only. It is not the planned sanitized published-pointer policy.
- `firestore.indexes.json:1-4` contains no planned indexes.
- `smoke:posting` performs a static rules check only; no rules-emulator suite or P11 gate exists.

Result: no production-bypass defect was demonstrated statically, and no Reader account/progress implementation or widened client write was found. However, browser readiness without interactive dev login was not reproduced against Firebase, and no emulator evidence exists. P11 is blocked/not implemented. No live token was minted and no policy was deployed.
